# v0.110 D1-Z：统一路由所有权与旧网络处置

## 1. 问题

v0.109 新增 `src/se/subject_vm/` 后，旧 latent router、working memory、knowledge policy residual、sparse selection、functional modules 和 candidate/group graph 的源码仍然存在。保留这些实现本身是必要的：大量历史配置、checkpoint、消融测试和 D1-X/Y 固定认知基线仍依赖它们。

真正的问题不是“旧文件还在”，而是此前没有代码级合同说明：哪些机制只是历史基线，哪些仍可作为客观存储或身体机制共存，哪些绝不能与 Subject VM 同时拥有行动路由权。若直接进入 Stage 3，项目可能形成两套并行的行动残差、状态和归因路径。

## 2. 本轮决定

新增 `subject-vm-routing-ownership-v1`：

1. inherited action strategy 保留为最低限度、角色中性的 sensorimotor/genetic-logit 基线；
2. 现有 action mask、categorical sampler、intent 和 world commit 仍是唯一物理行动权威；
3. Stage-2 Subject VM 启用时，它是唯一可选 action-potential residual owner；
4. legacy knowledge residual、latent router、working-memory router 和 sparse-selection router 保留为 fixed-cognition baseline，但禁止与 Stage 2 同时启用；
5. knowledge provenance store 继续保存客观内容和来源，不归 Subject VM 所有；
6. functional modules 继续作为身体/环境机制，不复制为主体图节点；
7. candidate subject graph 与 group graph 继续作为诊断和观测标签，不拥有主体图状态、行动 bonus 或 plasticity。

## 3. 代码处理

新增：

```text
src/se/subject_vm/ownership.py
protocols/decisions/subject_graph_vm_legacy_router_disposition_v1.json
```

`ownership.py` 只接收布尔化的窄配置视图，不 import knowledge、functional module、social 或 candidate graph 实现。它提供：

- 旧组件处置 registry；
- primary optional action route owner；
- Stage-2 并行路由冲突校验；
- 可用于诊断和文档校验的 machine-readable manifest。

`cfg.validate_config()` 在通用 Subject VM 配置校验后执行所有权校验。旧配置没有启用 Stage 2 时行为不变。Stage 2 与 legacy optional action route 同时开启时，在构建 Simulation 前即失败。

`policy.decide()` 另有防御性检查：即使未来某个调用者绕过配置校验，只要同一决策实际收到 legacy knowledge residual 与 Subject VM potential，就拒绝继续，而不是把两者静默相加。

## 4. 没有进行的迁移

本轮没有：

- 删除或移动 `knowledge/latent.py`、`knowledge/working_memory.py`；
- 把旧 latent gene 自动转成 Subject VM edge weight；
- 把 working memory 数组复制进 graph node state；
- 把 knowledge provenance、functional-module state、relation 或 group state复制进 Subject VM；
- 将旧 baseline checkpoint 伪装成已经形成的统一主体图；
- 实现 Stage-3 usage trace、credit、plasticity 或 reward。

自动转换会把旧系统的固定语义和历史结构伪装成“涌现图”，因此被明确禁止。未来若复用 sparse selection、quantized arithmetic 或 functional operator，只能先提取角色中性的窄 primitive，并由 Subject VM 节点/边身份调用。

## 5. 兼容性

- Subject VM disabled、Stage 1 或 Stage 2 未与 legacy route 冲突时，旧 config identity 不变；
- 旧 checkpoint 继续按原实现恢复；
- D1-X/Y、latent、working-memory 和 sparse-selection 测试仍可运行；
- knowledge store 可在关闭 policy influence 时与 Stage 2 共存；
- functional modules 可与 Stage 2 共存，因为它们作用于身体/环境结算而不是可选 action residual；
- candidate/group graph 可继续观测，但不能向 Subject VM 或 action logits注入值。

## 5.1 验证调度修正

新增测试文件会改变 round-robin shard 成员。部分 release/study/build 测试使用外部工具或固定工程资源，并发 shard 因此可能在单独运行均通过时发生跨 shard 竞态。`scripts/run_test_shards.py` 改为顺序执行五个独立 pytest 子进程：仍保留确定性文件分片、独立失败和逐 shard 报告，但不再让测试工具链并发修改共享工程资源。该修改不改变产品逻辑或科学语义。

## 6. 科学边界

路由所有权收敛只证明项目没有同时运行两个可选行动控制网络。它不证明：

- 旧网络已经被统一图吸收；
- Subject VM 已获得知识、记忆、利益或关系；
- functional module 是认知节点；
- retained node state 具有长期功能；
- 任意图结构能够通过演化形成；
- 已具备 Stage 3、Epoch 1 或主体性证据。

下一步只能在该单一所有权边界上冻结客观 event/usage trace。后果事实、实际使用节点/边和 later-tick update 必须分离，且不得重新创建独立 credit router。
