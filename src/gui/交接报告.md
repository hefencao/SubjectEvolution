## 一、项目概述

### 1. 项目目标

项目以 Python/CUDA 生态演化仿真为核心，使用 C++/raylib 提供高性能实时 GUI，用于观察：

* 环境资源与危险场变化；
* 大规模实体迁徙、采集、繁殖、死亡；
* 群体形成、群体移动与行为构成；
* 信任、压力、声誉、传闻等娱乐化社会循环；
* 单个实体及其局部环境、群体和社会关系。

长期定位不只是科研可视化工具，还希望支持游戏化、娱乐化和涌现叙事。

### 2. 核心架构原则

**Python 是仿真权威，C++ 默认只读。**

```text
Python / CUDA 仿真
    │
    │ 稳定状态快照
    ▼
共享内存三缓冲 eco_live.bin
    │
    ▼
C++ 接收线程
    │
    ├─ 环境渲染
    ├─ 实体与行为渲染
    ├─ 群体分析与轨迹
    ├─ Inspector
    └─ 娱乐化社会循环
```

重要约束：

* GUI 掉帧不能阻塞或改变 Python 仿真。
* C++ 社会循环属于展示和娱乐层，不应自动视为科研指标。
* C++ 不直接修改 Python 的实体数组。
* 未来若增加控制反馈，应使用独立命令通道，并只在 entertainment 模式启用。


## 三、数据链路

### 1. Python 发布端

共享帧包含：

* 四通道资源场；
* hazard；
* 存活实体 ID；
* group 和 lineage；
* 坐标与速度；
* energy、integrity、fertility、age；
* generation；
* action、target 和 success。

采用同机内存映射三缓冲：

* Python 写非当前槽；
* 完成 payload 后提交槽位序列；
* 最后更新全局发布序列；
* C++ 读取前后校验序列；
* 发现竞争则丢弃该帧，而不是阻塞 Python。

### 2. C++ 接收端

接收线程：

* 映射 `eco_live.bin`；
* 读取最新完整槽位；
* 将资源、危险和实体复制到复用的 `Frame`；
* 通过 pending/current 交换交给主线程。

共享内存协议、`mapped_file` 和 `shared_reader` 在后续渲染迭代中基本保持稳定。

## 五、v13.1 构建修复

v13 首次拆分后出现链接错误，原因不是函数缺失，而是新增 `.cpp` 未加入 `eco_game_runtime` 目标。

典型错误：

```text
undefined reference to eco::WorldRenderer::draw(...)
undefined reference to eco::WorldRenderer::observe_frame(...)
undefined reference to eco::render_lod_name(...)
```

必须在实际创建 `eco_game_runtime` 的 CMake 文件中加入：

```cmake
target_sources(eco_game_runtime PRIVATE
    src/renderer_internal.cpp
    src/renderer_core.cpp
    src/renderer_environment.cpp
    src/renderer_observation.cpp
    src/renderer_groups.cpp
    src/renderer_draw.cpp
)
```

`src/renderer.cpp` 可以继续保留。

修改 CMake 后必须重新配置：

```bash
rm -rf build

cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
```

若项目以 `src/gui` 为 CMake 根：

```bash
rm -rf build

cmake -S src/gui -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
```

### 重要性：P0

这是当前最先需要确认的事项。未正确注册拆分模块时，所有功能代码都无法链接。

## 六、已实现的主要功能

## 1. 连续 LOD

早期版本采用 Macro/Medium/Micro 硬切换，在约 `Zoom 1.0 → 1.1` 时出现非常突兀的画面跳变。

后续改为根据预计可见实体的屏幕间距计算连续权重：

* 人口密度权重；
* 实体权重；
* 微观细节权重；
* 流场权重；
* 环境清晰度。

界面中的 Macro、Medium、Micro 仍用于描述主要层次，但绘制图层不再完全互斥。

## 2. Macro

目标是观察整体生态趋势，而不是单个实体。

当前主要显示：

* 平滑环境资源；
* 人口密度；
* 一致性迁徙流；
* 大型群体的运动趋势；
* 群体历史轨迹；
* 聚合行为。

已移除或限制过的内容：

* 规则点阵人口标记；
* 大型人口峰圆圈；
* 满屏出生/死亡图标；
* 所有群体同时显示的大量重复箭头。

## 3. Medium

目标是观察群体分布和区域活动。

当前使用：

* 屏幕空间稳定抽样；
* 有限实体预算；
* 稳定 ID hash，减少实体闪烁；
* 实体主体颜色表示群体；
* 行为使用独立形状；
* 群体轨迹和群体行为叠加；
* group-focus 降低其他群体干扰。

## 4. Micro

目标是检查个体决策和局部环境。

当前支持：

* 可见区域内个体；
* 当前动作符号；
* 关系线；
* 行为目标；
* 选中实体高亮；
* 环境格和邻域；
* 当前资源梯度；
* 群体空间椭圆。


## 十、当前问题和风险

## P0：构建系统必须正式收口

当前已通过 v13.1 脚本补救，但最终应直接修改项目正式 CMake，而不是长期依赖应用脚本。

建议：

```cmake
set(ECO_RENDERER_SOURCES
    src/renderer.cpp
    src/renderer_internal.cpp
    src/renderer_core.cpp
    src/renderer_environment.cpp
    src/renderer_observation.cpp
    src/renderer_groups.cpp
    src/renderer_draw.cpp
)

target_sources(eco_game_runtime PRIVATE ${ECO_RENDERER_SOURCES})
```

并在 CI 中加入一次完整链接测试。

## P1：内部模块仍共享较大的 internal 接口

虽然已经拆成独立编译单元，但多个模块仍可能通过 `renderer_internal.hpp` 共享大量状态和辅助函数。

后续应逐步形成：

```text
EnvironmentLayer
AgentLayer
GroupLayer
SelectionLayer
ObservationCache
RenderContext
```

避免新的 internal 头文件再次增长成单体。

## P1：选择状态存在生命周期复杂性

已处理实体死亡后回退群体或清除选择，但仍需覆盖：

* 群体消失；
* group ID 复用；
* 切换运行流；
* 仿真重启；
* tick 回退；
* checkpoint 恢复；
* selected target 在下一帧消失。

## P1：群体统计成本

每个共享帧重新计算群体：

* 成员数量；
* 中心；
* 协方差；
* 行为构成；
* 平均速度。

实体规模继续扩大时，应考虑：

* 降频；
* 只分析活跃群体；
* 分块并行；
* 在 Python/CUDA 端预聚合部分群体信息。

## P2：行为和群体标记仍需视觉限流

最新画面已能观察群体，但以下内容仍可能重叠：

* 群体轨迹；
* 行为箭头；
* 群体椭圆；
* 关系线；
* 环境探针；
* 出生死亡事件。

建议统一建立基于屏幕面积的 overlay budget，而不是每层各自独立限量。

## P2：资源种类和资源语义有限

目前只有四个资源通道，且 GUI 不知道更具体的业务名称。后续应从配置或共享协议发送：

```text
资源名称
容量
单位
颜色建议
功能语义
```

否则界面只能显示 R1–R4。

## P2：环境显示仍属于观察近似

资源使用双标尺和显示增强，便于观察，但显示亮度不等同于绝对科学数值。

科研用途必须以 Inspector 原始值和 Python metrics 为准。

## P3：渲染后端性能上限

当前实体路径是 raylib/rlgl 批处理，已比逐个高级 API 调用高效，但不是：

* OpenGL instancing；
* 持久映射 VBO；
* GPU culling；
* CUDA/OpenGL interop。

数十万到百万实体时需要升级。
